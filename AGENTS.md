# VST workspace

Goal: build VST3 plugins, mainly MIDI-output sequencers (event out, little/no audio). macOS arm64, Xcode 26.5, CMake 4.0, Ninja available. Workspace root is a git repo (origin `github.com/dphelmer/vst-sequencers`, branch `main`); `build/` dirs are gitignored.

## Layout
- `vst3sdk/` — Steinberg VST3 SDK, tag `v3.8.1_build_84` (MIT), cloned `--recursive --depth 1` (submodules: base, cmake, doc, pluginterfaces, public.sdk, tutorials, vstgui4). Treat as vendored: do not edit. It is a git submodule of the root repo (pinned commit, detached HEAD); fresh clones need `git clone --recursive` or `git submodule update --init --recursive`.
- Plugins live in sibling dirs (e.g. `<plugin>/`) with their own `CMakeLists.txt`. Build output goes in `build/` dirs, not inside `vst3sdk/`.
- `transport-probe/` — MIDI-out probe plug-in for testing host transport behavior (Live). Template for new plugins: copy its `CMakeLists.txt` + `source/` layout (Processor + no-param Controller + `entry.cpp`, silent stereo audio out + event in/out, `PlugType::kInstrument`). Build: `cmake -S transport-probe -B transport-probe/build -G Ninja -DCMAKE_BUILD_TYPE=Release -DSMTG_CREATE_PLUGIN_LINK=OFF && cmake --build transport-probe/build --target TransportProbe` (validator passes 47/47). Offline logic test (fake transport, no host): `--target ProbeSim` then `transport-probe/build/bin/Release/ProbeSim`. User's plugins live in system `/Library/Audio/Plug-Ins/VST3` (not `~/Library`); install by hand with `cp -R` (not the symlink option). Ninja builds need the custom `mac/Info.plist.in` + `mac/PkgInfo` + re-sign step in `transport-probe/CMakeLists.txt` (copy it for new plugins): CMake's default plist is `APPL` with empty identifier, and Finder then shows the `.vst3` as a plain folder.
- `euclid/` — 4-channel Euclidean MIDI drum sequencer (fixed 16th-note steps, host-generic parameters only, no VSTGUI). Same build/install pattern as transport-probe (`cmake -S euclid -B euclid/build -G Ninja -DCMAKE_BUILD_TYPE=Release -DSMTG_CREATE_PLUGIN_LINK=OFF && cmake --build euclid/build --target Euclid`, validator 47/47). Offline sim: `--target EuclidSim` then `euclid/build/bin/Release/EuclidSim` (checks Euclidean patterns, 4-on-the-floor kick defaults, stop flush, loop wrap). Pattern core is pure (`source/euclidean.h`, `(j*pulses)%steps < pulses`); per-channel params (pulses/steps/rotate/pitch/velocity/gate/mute) + global MIDI channel (default 10). Transport logic mirrors transport-probe (ppq-only, cycle clamp, jump re-seat). Installed in `/Library/Audio/Plug-Ins/VST3`.
- Offline docs: `vst3sdk/doc/`. Online: https://steinbergmedia.github.io/vst3_dev_portal/

## Building a plugin against the SDK (verified)
Use the SDK as a subdirectory from the plugin's CMakeLists:
```cmake
cmake_minimum_required(VERSION 3.25)
set(SMTG_ENABLE_VST3_PLUGIN_EXAMPLES OFF CACHE BOOL "")
set(SMTG_ENABLE_VSTGUI_SUPPORT OFF CACHE BOOL "")   # ON only if using VSTGUI
add_subdirectory(<path>/vst3sdk vst3sdk)
smtg_enable_vst3_sdk()
project(MyPlugin VERSION 1.0.0)                      # VERSION is mandatory, else configure fails
smtg_add_vst3plugin(MyPlugin source/...cpp)
target_link_libraries(MyPlugin PRIVATE sdk)
smtg_target_configure_version_file(MyPlugin)         # needed if sources include "projectversion.h" (SDK example version.h does)
```
- Configure/build: `cmake -S . -B build -G Ninja -DCMAKE_BUILD_TYPE=Release && cmake --build build --target MyPlugin`
- Output: `build/VST3/<Config>/MyPlugin.vst3`.
- The SDK `validator` is built automatically and runs against the plugin as a POST_BUILD step (`SMTG_RUN_VST_VALIDATOR`); a build "fails" if validation fails. Binary: `build/bin/<Config>/validator <path>.vst3`.
- `SMTG_CREATE_PLUGIN_LINK` defaults ON: builds symlink the `.vst3` into `~/Library/Audio/Plug-Ins/VST3` (which already holds other user plugins — don't delete them). Pass `-DSMTG_CREATE_PLUGIN_LINK=OFF` for throwaway/probe builds.
- SDK default macOS deployment target is 10.13 and `SMTG_BUILD_UNIVERSAL_BINARY` defaults ON for Xcode generator; Xcode >= 15 gets an ad-hoc `codesign` post-build step automatically.
- Configuring the SDK standalone (`cmake -S vst3sdk -B <dir>`) builds all examples + hosting tools (validator, editorhost, audiohost); only for experiments. Harmless warning: LIBJACK not found.

## MIDI-output plugin notes (from SDK headers/samples)
- Reference sample: `vst3sdk/public.sdk/samples/vst/legacymidiccout/` (emits events via `data.outputEvents->addEvent`) and `note_expression_synth/`, `again_sampleaccurate/`.
- Declare output with `addEventOutput(STR16("Event Out"), 16)` in `Processor::initialize` (`public.sdk/source/vst/vstaudioeffect.h`). Add `addEventInput` for MIDI-in-driven behavior.
- Plugin category (in factory class info) is `PlugType::kInstrument` or `kFxInstrument` (`pluginterfaces/vst/ivstaudioprocessor.h`) — host decides whether it can be placed on an instrument/MIDI track from this plus bus config; test in the target DAW.
- Sequencer timing comes from `data.processContext` (`ProcessContext` in `pluginterfaces/vst/ivstprocesscontext.h`): check `state` flags (`kPlaying`, `kTempoValid`, `kProjectTimeMusicValid`, `kTimeSigValid`) before reading `tempo`/`projectTimeMusic`; they are optional. Event `sampleOffset` is relative to the block start and must be < `numSamples`.
- Note on/off: `Event::kNoteOnEvent` / `kNoteOffEvent` need matching `noteId`; send note-offs on transport stop / deactivate to avoid stuck notes. Raw CC/pitch-bend/etc. out requires `kLegacyMIDICCOutEvent` (`Helpers::initLegacyMIDICCOutEvent`), host support varies.
- `process()` is realtime: no allocation, locks, or I/O.
- Parameter display: hosts show the SDK default normalized 0..1 float unless the controller overrides `getParamStringByValue` / `getParamValueByString` / `normalizedParamToPlain` / `plainParamToNormalized` (`ivsteditcontroller.h`). Keep plain<->normalized conversion in one shared header (`params.h` in euclid) and have both controller (display) and processor (decode) use it, so shown values can't drift from played values. Note: `Steinberg::Vst::String128`/`TChar` (not `Steinberg::`), `UString` needs `pluginterfaces/base/ustring.h`, and a plugin-local `enum ParamID` shadows `Steinberg::Vst::ParamID` in `using namespace` scopes — qualify. Covered by the string round-trip section in `tests/sim.cpp`.
- Processor and controller are separate classes with distinct CIDs (`plugcids.h` pattern); never reuse the SDK sample FUIDs for real plugins — generate new ones.
- Trademark: don't put "VST" in the plugin/company name.

## Transport sync / Ableton Live (target host)
Sources: SDK headers + Ableton help + JUCE forum reports (community), plus **VERIFIED-IN-LIVE** items measured with `transport-probe` (Live on macOS arm64, 44.1 kHz, 512-sample blocks; Live version not recorded). Anything marked UNTESTED still needs a probe run.
- **Request transport fields or get none.** `ProcessContext` fields are only filled if the plugin asks via `IProcessContextRequirements` (since SDK 3.7, header says you "may not get any information at all" otherwise). `AudioEffect` implements it but defaults to flags 0 and the validator still passes. In the Processor constructor: `processContextRequirements.needTransportState().needProjectTimeMusic().needTempo().needTimeSignature();` (add `.needBarPositionMusic()`, `.needCycleMusic()` if used). Flags are read once between `initialize` and `setActive`; can't change later.
- VERIFIED-IN-LIVE with the requirements flags set: transport state, `projectTimeMusic`, tempo, time sig, bar position, cycle range all valid every block (stopped too); `kSystemTimeValid` was NOT set. `projectTimeSamples` was 0 while stopped.
- Still check the `state` valid flags every block; `projectTimeSamples` and `sampleRate` are the only always-valid fields.
- **Live VST3 has no "MIDI effect" slot.** VST3 has no MIDI-effect category and Live won't put third-party MIDI plugins before an instrument on one track. Pattern: sequencer plugin on its own MIDI track, second MIDI track with `MIDI From` = sequencer track + plugin channel, monitor `In`, instrument on that second track. VERIFIED-IN-LIVE: the lower `MIDI From` chooser must be set to the plugin itself (`TransportProbe`), NOT `Pre FX`/`Post FX` (that was the cause of 'probe emits nothing'; probe log showed events were emitted fine) (Ableton help "Accessing the MIDI output of a VST plug-in"). Live merges all MIDI channels when routing track-to-track, so don't rely on channel to split lanes.
- **Workaround for the channel merge: CoreMIDI virtual source from the plugin.** VERIFIED-IN-LIVE (2026-10-15, Live 11.3.43, macOS 26 arm64): plugin creates a virtual MIDI source (`MIDIClientCreate` + `MIDISourceCreate` in `initialize`, dispose in `terminate`; see `transport-probe/source/virtualmidi.cpp`), sends notes via stack `MIDIPacketList` + `MIDIReceived` from `process()`; Live tracks take it via `Ext. In` → port → per-channel Input chooser, and channels 1–4 are preserved (unlike track-to-track routing). The port must be enabled with **Track** in Live's MIDI settings (port appears after the plugin is first loaded). This makes single-instance multi-lane sequencers viable in Live (one lane per channel). Caveats: offline bounce is broken (virtual MIDI arrives in real time while the plugin runs offline — fine for live-performance-only products); timestamps are ASAP per block (buffer-size jitter, not sample-accurate); `MIDIPacketListAdd` MUST get the pointer from `MIDIPacketListInit` as `curPacket` — passing NULL crashes Live (segfault in `MIDIPacketListAdd`, hit 2026-10-15); `MIDIPacketListAdd` is deprecated (replacement `MIDIEventListAdd`, macOS 11+) but works.
- **Must declare an audio output bus** (e.g. stereo, silent) and be an instrument category, or Live refuses to load a pure-MIDI VST3 (JUCE forum; JUCE's own MidiLogger special-cases Live for this). VERIFIED-IN-LIVE: an instrument-category plug-in with **no event input bus** is also refused at device creation (`Log.txt`: "plugin has instrument category, but no valid event input bus" → "Failed"), even if it only generates MIDI — always call `addEventInput` (Euclid shipped without it and Live refused; the SDK validator did not catch it, 47/47). Debug Live load failures in `~/Library/Preferences/Ableton/<Live version>/Log.txt` (exact error) and `PluginScanner.txt` (scan time).
- **Note on/off VERIFIED-IN-LIVE to reach the routed track** (note-on at exact ppq beats). CC1 (legacy MIDI CC out) also VERIFIED-IN-LIVE to arrive on the routed track (user-observed, Live version not recorded). Older JUCE forum threads (2020-2022) reported `kLegacyMIDICCOutEvent` doing nothing in Live VST3, but CC1 works with the probe on current Live; pitch bend/other CC numbers not individually tested. AU can't do MIDI out at all (Ableton help), so VST3 is the right format.
- **Derive position from `projectTimeMusic` (ppq) at block start, not from `projectTimeSamples`.** VERIFIED-IN-LIVE: `projectTimeSamples` jumps (non-linear) on every block where tempo changes (83/83 in a tempo-ramp run); ppq stays continuous (error ~5e-4 beat on the changing block). Tempo changes mid-block are not visible until the next block, so compute step boundaries per block as `ppq + (sampleOffset/sampleRate) * tempo/60` and accept small drift on tempo ramps.
- Detect jumps (loop wrap, locate, clip relaunch) by comparing this block's ppq to the previous block's expected ppq (`prev + numSamples/sampleRate*tempo/60`); on a jump, send note-offs for held notes and re-seat the step index. Host may not split blocks at loop points (documented as optional). VERIFIED-IN-LIVE (Arrangement loop): Live DOES split the block at the loop end (e.g. 346 + 166 samples); the second block starts at exactly `cycleStartMusic` and jump detection (ppq != prev expected end) fires once per wrap. `kCycleActive` is set only when the loop is enabled (it was never set in the first run with the loop off; `kCycleValid` + `cycleStartMusic`/`cycleEndMusic` are valid regardless, even while stopped) and can stay set while stopped. GOTCHA: ppq-from-tempo block end can overshoot `cycleEndMusic` by ~1e-5 beat, which fires a ghost note on the loop-end beat one sample before the real loop-start note; when `kCycleActive` and `p0 < cycleEnd < p1`, clamp `p1 = cycleEnd` (done in transport-probe, covered by ProbeSim).
- Transport stop: when `kPlaying` goes 1->0 flush note-offs for notes this plugin started (track them; don't blast 128x16 note-offs). Also flush in `setActive(false)` / `setProcessing(false)`. VERIFIED-IN-LIVE: Live keeps calling `process()` while stopped (~85% of blocks in a test run) with ppq frozen at the playhead, so gate generation on `kPlaying`.
- Session View clip launch is quantized by Live's launch quantization, but the plugin only sees the global transport/ppq; a sequencer plugin on a MIDI track is not clip-aware. Don't expect clip-relative position. Session clip launch worked with the probe (user-observed notes kept playing on the grid); exact ppq behavior with Arrangement stopped not logged.
- Live compensates plugin latency (PDC). A MIDI-only plugin should report 0 latency; MIDI from the plugin reaches the routed track through the host. Track-to-track latency VERIFIED-IN-LIVE as correct: recorded notes from the routed track land on the grid (user-observed; no numeric offset measured).
- Live (at least 11) has been reported to not set `processMode` to `kOffline` during export; don't rely on it to detect bounce.
- SDK `host-checker` sample (`public.sdk/samples/vst/hostchecker`, needs `SMTG_ENABLE_VSTGUI_SUPPORT=ON`) reports which `ProcessContext` fields a host actually provides. It's an audio FX with no event I/O; build with `-DSMTG_CREATE_PLUGIN_LINK=OFF` and copy manually if wanted. A purpose-built MIDI-out "transport probe" plugin is a better first test in Live.

### Transport probe: how to run it in Live
- Plug-in emits note on at every quarter-note boundary (pitch 72 on bar downbeat, else 60; off 0.25 beat later) plus legacy CC1 on the same beats, only while `kPlaying`. The same notes/CCs are ALSO mirrored on the CoreMIDI virtual source "TransportProbe MIDI" across channels 1–4 (for the channel-preservation test). It logs to `~/Library/Logs/TransportProbe/` (`blocks.csv` per process block, `events.csv` incoming events, `lifecycle.log`); files are truncated on each `setActive(true)`, so one instance at a time. Summarize with `python3 transport-probe/tools/analyze.py`.
- Test matrix (answers the UNTESTED items above): stop/start; Arrangement loop; locate while playing; tempo ramp/change; Session clip launch with Arrangement stopped; export/bounce; read analyze.py output for `kCycleActive`, calls-while-stopped, jumps, processMode. For latency/CC: route to a second MIDI track (see pattern above), record into a clip, check note position vs grid and whether CC1 arrives.
- Verified in Live so far: notes at exact beats, Arrangement loop wrap, tempo ramp, Session clip launch, virtual-port multi-channel delivery (channels 1–4 preserved via Ext. In) (user-observed). Still unmeasured: export/bounce (virtual-port path expected broken).
